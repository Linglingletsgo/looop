# backlog-prioritization

Inspect current backlog, confirmed inputs, code, dependencies, active goals and recently delivered work. Verify a candidate is still missing and is permitted. A controller-selected confirmed requirement takes precedence; do not substitute unrelated busywork.
Compare candidates by user impact, evidence confidence, effort, dependency readiness and alignment with approved direction. Use RICE or other numerical scoring only with real inputs; otherwise state qualitative tradeoffs and unknowns. No fixed top-five quota or arbitrary preference for tiny changes.
Choose one meaningful outcome with observable success criteria and the next coherent slice. Explain why now and why the alternatives wait. Already-understood bugs or authorized backlog work need proportionate repository validation, not a new market study.
If no valuable item is ready, return no_work with the concrete blocker. Do not discover new requirements when the operator selected backlog-only.
