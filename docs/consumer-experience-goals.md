# 消费级产品体验目标

新选题从普通用户完成一件事的完整旅程出发：意图输入、等待过程、理解结果、采取行动。先说明实际障碍与前后变化，再决定实现切片；不能以容易补边界测试作为产品价值的替代。技术正确性、可靠性和基础设施仍可优先，但要说明它们怎样影响用户完成任务。不要为了显得升级更大而发明功能。

新体验目标可包含：

```json
{
  "experience": {
    "journey": "描述投稿需求、比较候选、打开合适的投稿入口",
    "before": "用户难以比较候选，也不知道下一步",
    "after": "用户无需阅读说明即可选择候选并进入行动",
    "criterion": "用户能从结果页选择一个候选并打开对应投稿入口"
  }
}
```

criterion 必须逐字出现在同一目标的 success_criteria 中。目标创建后保持不变；实现可以跨多轮开发、独立审核和多个 PR。既有目标不追加强制字段。库、CLI 或后台工具不强制引入 UI 旅程。UX/UI 仅按项目工作流和任务需要参与，不增加默认 Product 或 Acceptance 阶段。

## 体验验证

Packet 的完成判据应包括获授权的实际运行检查，以及适用的空结果、加载、错误恢复、成功和可访问性行为。测试及代码审核继续保留；截图和通过的测试不能单独证明可用性。

体验目标关闭时，其体验判据至少需要一个 completion_evidence：

```json
{
  "criterion": "用户能从结果页选择一个候选并打开对应投稿入口",
  "kind": "agent_walkthrough",
  "target_sha": "<当前完整提交 SHA>",
  "path": "experience-walkthrough.txt",
  "quote": "<走查记录中的逐字结果>"
}
```

path 相对于规划提示中给出的体验产物目录。PM 在实际运行获授权的产品后保存有界记录：旅程、观察到的界面/交互状态、结果、限制及提交版本。agent_walkthrough 是代理走查；user_test 只用于确实开展且获授权的真实用户测试，不能把代理判断宣称为用户满意度。没有真实用户测试不妨碍明确标注的代理走查，但不能据此声称获得真实用户验证。

调度器检查判据覆盖、SHA、文件路径及引文存在；这些只证明记录身份与可追溯性，不证明体验判断正确。PM 负责解释，独立审核仍负责检查实现与证据。缺少运行环境时留下具体验证缺口，不能虚报完成或用无关小修补代替。结果记录覆盖当前状态，诊断按现有保留策略清理。

## 部署边界

规划与研究收到相同的体验原则，Magpie 的通用 PM 也同步这些指令。默认角色源文件的哈希保持稳定，避免让已绑定交付因角色基线变化受阻。WOS 角色、工作流和文件不变；GTP 已绑定任务及当前目标保持原契约，新目标才采用新结构。

本次不自动升级各项目导出的 product_goals.py/project_state.py；旧版独立工具不会理解新增体验契约，升级前应避免用旧工具操作新体验目标。新版 looop 调度入口直接使用新校验逻辑。
