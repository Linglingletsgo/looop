# looop

Personal agent scheduler and Paperclip customization. One maintained repository for scheduling, adapters, default roles and skills.

- `bin/`: controller, standalone state tools and Paperclip integration.
- `skills/project-adapter/`: project onboarding skill; assets link to canonical code.
- `default-roles/`: concise fallback roles; project roles take precedence.
- `runtime/`: pinned Paperclip npm manifest and lockfile.
- `retention.json`: bounded diagnostic retention.
- `tests/`: Linux verification.

Each project owns `.agent/local/runtime/data/project-state/state.sqlite` and `current.json`. Paperclip and independent conversations use this same state. Controller `locations.json` stores local routing only. `.agent/project.json`, `.agent/tools/` and a short AGENTS entry provide the portable project interface. Historical HANDOFF is reference, not current state.

Independent project: `python3 .agent/tools/project-session.py context --repo .`. Use start/progress/finish to update current work; start must be accepted before assuming scheduler exclusivity. No periodic handoff or conversation transcript is required.

Install from a clone on Linux: `python3 bin/setup.py` (Node24+, Python3, Git). Reconnect local credentials and project paths; these are intentionally excluded from Git. GitHub preserves the scheduler code, not secrets or live business state. To move active work, transfer each project's ignored state directory securely and relink it; do not run two schedulers against divergent copies.

Existing installation: `/home/agentdev/projects/looop`. Legacy compatibility paths have been removed. Paperclip remains at its existing Tailscale address. The owner landing page is `/looop`, an authenticated project-loop console. `/?paperclip=1` opens the original Paperclip UI. The version-checked `bin/install-ui.py` mounts source-managed UI routes after Paperclip authentication; setup reapplies it after dependency installation. It does not edit minified UI bundles. Opening the console never resumes planning. Owner actions use same-origin JSON, project revision checks and the same project-owned state as independent conversations.

Retention: log/trace tails ≤2MiB each; 500 recent acknowledged project events plus up to5000 pending events; latest20 self-reported completions; terminal current-state summaries retained as needed. Completed diagnostic workspaces compact after14 days,20 runs or1GiB. Active tasks, unresolved decisions and unsynced events are protected. Current-state mutation never requires replaying full logs. Legacy pilot snapshots are not execution truth and will be separately inventoried.

Run `python3 -m unittest discover -s tests` and `node tests/console-http.mjs` (after runtime setup). `docs/history/` is migration reference, not required reading or the current operating contract.

Console operations:
- **Selection source** defaults to **Backlog only**. Confirmed requirements in current state have priority; otherwise PM selects an explicit pending `- [ ]` entry from the adapter’s `backlog_paths` (or declared backlog reference files). Historical prose and checked entries are context, not pending work. For older free-form backlogs, the adapting agent should put genuinely pending requirements into current state or a short checklist after checking code; do not convert historical work blindly. Empty backlog sleeps without a model call. **Backlog + research** also permits finding requirements within current product direction. It does not authorize outside scope, external network research, new providers or new services. Selection changes increment `planning_revision`, reject stale undispatched proposals and leave bound deliveries intact. The chosen backlog item is linked to the delivery so it cannot be selected repeatedly.
- **Execution settings** default to unlimited daily autonomous proposals. Each project can set a positive daily count or clear it for unlimited; `loop_limits` in project-owned state is authoritative. Custom daily limits reset on UTC dates and exclude confirmed requirements. Settings do not change loop mode, scope or review gates.
- **Once / continuous / pause** update `loop_control` in project-owned state. Once claims at most one PM attempt and waits through delivery/mainline verification before stopping; no-work also stops. Pause drains started work and prevents new selection. The timer launches configured lanes in separate tmux sessions. Legacy `enabled` is only the fallback before an explicit state switch; CLI and UI then share the same state. No total-duration kill is imposed.
- **Product input** stores confirmed requirements or decisions; it never resumes a paused loop or expands execution authority. Requirements enter PM priority selection; decisions constrain planning. Independent conversations read the same state.
- **Attention** resolves existing change requests (keep the original scope or follow up separately), returns deferred requirements to PM, and shows bounded task evidence. Explicit retry uses existing worker/lock/baseline/publication checks, retains evidence and reruns gates. Unknown publication/PM effects are not blindly replayed; provider auth/credit issues still need verification.
- **Onboarding** previews arbitrary project roles, mapped workflow, checks, lockfiles and CLI availability without executing project scripts. Explicit connection preserves existing rules and creates a context-only adapter when missing, standalone state tools, a short AGENTS entry and an ignored project-owned state directory. It adds an observation project without agents, execution policy, credentials, installs, commits or pushes. Linked worktrees remain preview-only. Complex/conflicting mappings and existing state/tool mismatches must be resolved in the project conversation using the adapter skill. A version fingerprint prevents using stale previews. Ambiguous board creation results are reconciled by marker rather than reposted.

Keep company/agent configuration in advanced Paperclip views. Dependency preview is static: a detected CLI does not prove services/system libraries are operational. Activation uses the existing project contract and verified environment. A context-only adapter stays non-executable until its mapping is completed in the project conversation; WOS stays disabled and DS1 stays manual.

Scheduling authority lives in project `loop_control`; product decisions retain direction, scope and approval constraints. To replace an obsolete decision, submit human-confirmed `supersede_decision` with `intent_id`, replacement `title`/`body`, expected revision and stable request id. The original remains linked audit history, while normal context and PM input include only effective decisions. Starting a loop never grants broader implementation scope.

Execution configuration no longer requires a second per-project file whitelist. For a registered lane with a verified profile and an executable `.agent/project.json`, run `python3 bin/delivery-control.py configure LANE` on Linux. It inherits project roles, workflow, checks and explicit restrictions. When no project workflow exists, `runtime/execution-defaults.json` supplies Builder (Command Code) → Reviewer (Codex), with optional local overrides in ignored `data/execution-defaults.json`. Command Code remains routed only to the configured DeepSeek Flash subscription; there is no paid fallback. No Acceptance step is added. Existing execution policies are preserved; `--policy FILE` remains an explicit override for special projects. Configuration does not start a loop or change merge policy.

Without a project file whitelist, PM proposes task-specific paths and Builder is checked against that immutable task scope. Native AGENTS, project role/rule files and secrets remain protected. This reuses the project contract, not the terminal session’s unrestricted host environment: credentials and publication remain controller-owned, and jobs run in isolated snapshots. Python, Node and npm script checks are supported; npm uses the installed distribution and mounted project dependencies without host npmrc. Other package managers, network services and checks needing writable build directories require an adapted execution environment; they are not silently replaced or declared verified.

Selection CLI, using the same project-owned state as the UI: `python3 bin/autonomy-control.py select LANE --selection-mode backlog_only` or `--selection-mode backlog_and_research`. This changes only task selection; use the normal once/resume action to start execution. In the console open **Execution settings → Selection source**, save, then choose **Once** or **Continuous**.

The console header’s **Execution settings** edits Harness and Token Plan routes for planning, Builder, Reviewer, optional Acceptance and advice. The current harness adapter is Codex CLI; Claude Code and pi are displayed as unavailable until their adapters exist. Codex uses CLIProxyAPI, with an optional model override; Command Code stays fixed to DeepSeek Flash. Global settings are revision checked, stored in ignored `data/execution-settings.json`, and contain no secrets. Saving does not launch projects. Each newly started planning/delivery captures its settings; running stages keep their captured routes. Without an explicit settings save, existing project provider mappings remain in effect.

Unconfigured project cards expose **Prepare automatic development**. The read-only check lists contract, workflow, check-command, baseline, checkout and unsupported runtime gaps. Ready projects can enable configuration without starting tasks; uncertain Agent creation is journaled and never blindly retried. WOS currently requires its own workflow mapping and source-free black-box acceptance, which the current source-visible delivery runner does not implement; it therefore remains blocked rather than silently using the generic review pipeline. Its uncommitted/untracked work and DS1 remain untouched.
